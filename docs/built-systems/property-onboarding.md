# Property Onboarding — Rules

Canonical sources: `src/lib/kb-extractor.ts` (synthesis), `src/components/dashboard/onboarding/` (UI), `src/app/api/onboarding/`. Hyper-local location intelligence is a self-contained layer: start at `src/lib/hyper-local/index.ts`, whose header maps every file in it.

---

## Rules

- **Never fabricate property facts.** The knowledge-base synthesizer operates under a strict fact-vs-copy split: marketing copy may be written, but specs, lease terms, and policies may only be restated from spoken input. Inventing an unstated term is the worst failure mode in this system — it puts false claims into a sales agent's mouth. The same rule applies to the UI: the review card renders "Not specified" for a missing term; never substitute a plausible default such as "No HOA fee" or "Available immediately".
- **Never block Agora WebRTC voice turns on LLM extraction.** Turn-level extraction runs asynchronously out-of-band using Gemini with an attention scratchpad (`spokenSummary`) and required nullable core schema. It dispatches only upon finalized user turns, to extract in parallel while Elena begins speaking; agent turns never dispatch it. Requests are managed via a **Trailing Conflating Queue**: in-flight requests are never hard-aborted; fast subsequent turns coalesce into a single follow-up call once the active extraction completes. The WebRTC voice audio stream flows continuously with zero interruption or audio latency. Continuous listening stays active throughout the call to capture verbal corrections.
- **Never feed the extractor user-only transcripts.** Always include labeled assistant turns (`[ELENA VANCE]` and `[OWNER]`) so the model can repair ASR speech-to-text phonetic slips from question and confirmation context — and never let assistant text be treated as owner facts.
- **Never let end-of-call synthesis clobber live verified attributes.** Live verified specs on screen are immutable ground truth; post-call synthesis enriches descriptions, sales pitches, FAQs, and negotiation rules, but must never overwrite verified specs with empty or ungrounded values.
- **Never pre-fill the inspector pane with empty form fields.** Parameters are revealed only as they are genuinely detected. The design intent is that visible state always reflects real extracted data, so an owner can trust the checklist.
- **The deploy action stays locked until every required attribute is verified.** Do not add a bypass.
- **"Core specs verified" has one definition: `getCoreSpecStatus` + `getCoreSpecRows` in `src/components/dashboard/onboarding/inspector-specs.ts`.** The checklist, the deploy lock, the studio's review-card gate, the review card, and the end-of-call merge all consume it. `getCoreSpecStatus` answers every key honestly; `getCoreSpecRows` decides which seven of them this listing is judged on. A bedroom count of 0 is verified only when the title or description says "studio"; a bare 0 is an unstated count. Never re-derive the rule in a component: three copies once disagreed, and the review card could open with bedrooms unknown. **Never hard-code the count either** — the checklist, the review card's "n of m filled in" and the inspector's badge all read `items.length`, because a commercial listing swaps two rows rather than adding an eighth.
- **A commercial listing has no bedrooms and no bathrooms; those two rows are replaced, not left blank.** Office, shop, showroom and warehouse are judged on carpet area, washrooms and furnishing status instead. Before this existed, `getCoreSpecStatus` required `bedrooms > 0` and `bathrooms > 0` unconditionally, so a commercial property could never reach 100% and could never be deployed — the deploy lock has no bypass, so an unreachable row is a dead listing. Commercial washrooms are frequently qualitative ("provided by the tower", "common on floor"): `turn-extractor` populates `washroomDetail` and records `washrooms: 0` for shared facilities; `getCoreSpecStatus` verifies washrooms if either a numeric count or a non-empty `washroomDetail` is present. Never treat tower/shared washrooms as silence.
- **Property type is never a default. An unstated type is `""`.** `properties.property_type` deliberately has no DB default and the column dropped the `"apartment"` one it used to carry, because that default wrote a false claim about every listing nobody had described — and `buildAdditionalSpecs` then hid the row whenever it equalled `"apartment"`, so the fabricated value was invisible on screen while being persisted, served to buyers, and read by the sales agent. Both extractor prompts forbid guessing it. This is the fact-vs-copy rule applied to the one field that used to be exempt from it.
- **Property type carries only the property type; floor and unit numbers belong to location and address.** The Property Type row displays solely the type itself (e.g. "Office Space", "Flat / Apartment") and verifies as soon as a valid property type is selected or stated. Floor number and unit number (e.g. "Unit 121, 2nd floor") are formatted and displayed under Location & Address via `formatCompositeAddress` and persisted cleanly into their respective database columns (`floor_number`, `unit_number`).
- **Never derive a floor from a unit or flat number.** "Flat 402" is not the 4th floor — the convention is not reliable, and inventing the floor from it is exactly the plausible-default fabrication the review card's "Not specified" rule exists to prevent. Both prompts say so explicitly. A two-word question is cheaper than a confident wrong answer.
- **Natural address and location intake without artificial bundling.** Once listing type and property type are stated, Elena Vance asks for the street address, unit/floor, and city naturally. The extractor parses `unitNumber`, `floorNumber`, `address`, and `city` independently without conflating unit numbers (e.g. "121") as floors.
- **A tapped answer must never be announced back into the call.** `ExtraSpecsSuggestionBar` writes straight to state through `onApplyChip`. Elena cannot see a tap — injecting a synthetic RTM message to tell her is banned above, and remains banned here — so she may ask once more for something already tapped. That is the accepted cost: the checklist and the deploy gate read state, not Elena. **Stage 1 core specs are spoken only**: the matching `CoreSpecsSuggestionBar` was deleted on 2026-09-10, so tapping now exists for Stage 3 additional specs alone.
- **Never trigger the Review Specs modal via automatic all-verified thresholding or synthetic RTM text injection.** Modal presentation is strictly conversational or user-driven (via Elena's verbal completion cues, explicit owner voice commands like "pull up / show the review card", or manual UI clicks). The UI coordinates via an **In-Flight Sync Gate**: because user-turn extraction runs in parallel while Elena speaks, all core specs typically land before Elena reaches her review card announcement. If Elena or the owner requests opening the review modal while an extraction is still resolving in the trailing conflating queue, the UI latches the open request (`pendingModalOpenRef`) until the in-flight extraction lands in state. Once extraction completes, the latch auto-releases and opens the card so the owner is never locked out from reviewing or completing specs. **Injecting synthetic RTM user messages mid-call is strictly banned**: it causes Elena to read bracketed prompt cues aloud, aborts ongoing speech playback, and creates conflicting turn states that cause Google Gemini to reject requests with `400: Requests ending with a model turn are not supported`.
- **Listing-URL scraping was removed on 2026-09-09. Never re-add a crawler or URL-import path to onboarding.** The studio ingests property facts by voice only. An Apify-backed "paste a listing URL" bar once sat at the top of the conversational panel and fed the same synthesizer; it was deleted by product decision, not left unbuilt. Re-adding one also reopens the fabrication risk the fact-vs-copy rule above guards: crawled marketing copy reads as owner-stated fact to the synthesizer.
- **Gemini is the only synthesizer. Never add an offline, regex, or heuristic fallback.** When Gemini is unconfigured, unreachable, or returns nothing, `extractPropertyKnowledgeBase` throws and the studio shows the error beside the transcript. The heuristic that once stood in for it silently produced thinner, unverified knowledge bases with no error, which the fail-fast contract forbids.
- **Owner identity is pre-authenticated and concise**: Elena Vance must address the owner by their account first name (`"Hi {firstName}! I'm Elena. Let's get your property out to buyers and tenants..."`, using fallback `"Hi there!"` if display name is blank) and weave in confirmation of their contact email. **Never inject synthetic or premature greeting placeholders into the transcript before microphone permission is granted and RTC is joined** — transcripts must be driven exclusively by Agora's live real-time speech stream to prevent ghost messages and replacement flicker.
- **The studio opens in three entry stages, and the conversational panel must never unmount between them.** `intro` is a small centred card over the dimmed studio (Elena, the signed-in owner, Start); `focused` grows it into a full-width chat for Elena's opener; `split` flies it left and brings in the inspector. This axis is independent of the `onboardingStage` machine, which tracks how far the interview has got rather than how the screen is laid out. The panel owns the live Agora RTC client, so gating it on a stage (`entryStage === "x" && <ConversationalPanel/>`) drops the call the moment the stage changes. Only the wrapper class strings change; the panel is rendered unconditionally.
- **The microphone is acquired before the Agora session exists. Never move the request back inside `startCall`.** Agora asks for the mic at step 4 of its connect sequence, *after* `/api/agora/session/start` has already created a billed session, so a refused mic used to cost a session and the browser prompt landed in the middle of the connect. The Start handler calls `getUserMedia` first, stops the tracks immediately (Agora opens its own), and only then starts the session. A denial shows on the card and creates nothing. Two paths that are not a prompt must both keep working: an already-granted mic resolves instantly with no prompt at all, and a denial rejects with a `NotAllowedError` `DOMException`.
- **The inspector appears when the first turn extraction settles - never when it yields content.** The trigger is `isTurnSyncing` going true then false, which `executeTurnExtraction` clears in a `finally`, so a 15-second timeout or a failed extraction reveals the pane too. Gating the reveal on extracted specs instead would strand the inspector off-screen for an owner whose first answer was "hi", with no way back. Reconnecting after a mid-interview Disconnect must not replay the intro growth: the idle card returns inside the split layout, and only a Start pressed from `intro` may grow it.
- **The entry-stage class strings must never carry a transform, and the card's height must never be a percentage of a content-sized parent.** Both were shipped and both broke the intro card. `inset-0` + `m-auto` + a content-driven height is over-constrained, and it made the card's height depend on its content while the panel root's `h-full` made the content depend on the card's height: Chrome and Edge break that circle by treating the percentage as `auto`, Safari resolves it to 0, and the card rendered as a 2px line - its borders - with the persona block squeezed to its 41px of padding and every child shrunk away. Centring with `-translate-x-1/2` instead put a transform on the class, which *compounds* with the inline transform the flight writes rather than being overridden by it, so the card set off from the wrong position and swung 128px past the left edge. Centring is now the same full-screen flex container the studio's other modals use, with the card an ordinary flow child sized by `PANEL_CARD_CLASSES`. **Verify entry-stage layout in real Safari, not only in Playwright's WebKit** - Playwright's build resolved the circular height the way Chrome does and never reproduced the collapse.
- **Never pass the `inset` shorthand in the same `gsap.set` as `left`/`top`.** `inset` is a shorthand for all four offsets and GSAP does not guarantee it is written before the longhands; it silently clobbered them, so the card began every flight at the container's left edge instead of its recorded position and sailed off screen. The entry choreography is a hand-rolled FLIP - it measures both rects and pins the card to explicit fixed geometry for the flight. GSAP's Flip plugin was measured against it and performs identically, so swapping to Flip is a legitimate refactor, not a fix; the hand-rolled version is simply the one that has been verified here.
- **Two-tier onboarding flow**: Elena Vance verifies the seven core specifications first and opens the Core Specs review card. Additional property specs (parking, utilities, HOA, availability) are gathered only after the owner confirms the core specs.
- **Never ask home sellers for a universal pet policy**: Pet policies are strictly rental-specific; asking a seller for a pet policy on a single-family home violates natural real estate conventions. On sales, pet bylaws are scoped strictly to condo/co-op HOA inquiries.
- **Never use viewport-level `scrollIntoView()` for live transcripts**: Transcript auto-scrolling must stay strictly confined to internal container `.scrollTo()` to prevent ancestor scrolling from pushing sticky call controls (Elena Vance's avatar, status, and the Disconnect button) out of the viewport.
- **Listing type is permanently locked once established**: In Stage 1, once `listingType` ("rent" vs "sale") is chosen, it cannot be changed verbally later in the session because the entire subsequent dialogue structure and intake questions branch directly on it. All other specs remain continuously editable.
- **Assistant turn intent deduplication policy**: Each assistant turn intent must be keyed (`assistant_${turnId}_${intent}`) so an assistant announcement fires only once per turn. Evaluating un-deduplicated historic assistant transcripts re-triggers past intents across stages and is strictly prohibited.
- **The hyper-local location search is dispatched once per session, at core-spec confirmation.** `triggerLocationEnrichment` latches before the first fetch, so every later call site is a no-op. Several conversational paths legitimately reach that transition more than once in a session, and each extra run is a duplicate real-world Maps fetch the owner watches happen twice, not a retry. **One automatic retry, and only on a dead result**: a 5xx, a transport or parse fault, or a result naming zero places (no metro, highways, schools or hospitals) buys a second attempt after a short backoff, capped at two. A 400 or 401 is never retried — a rejected address and an expired session fail identically however often we ask — and neither is an ungrounded result that still names places, because grounding is flaky enough that retrying it would make a double search routine. `triggerLocationEnrichment` owns both attempts, so any external call once it has run is a duplicate. Never add an owner-facing "search again" control.
- **Never surface model or vendor names in the onboarding UI.** The hyper-local HUD and the review card's nearby-places section name the capability, never the LLM that powers them. Vendor names belong in the Telemetry HUD and code comments only. "Google Maps" is exempt — it is the real-world data source the owner is being asked to trust, not a model brand.
- **Strict Stage Isolation for Review Modals**: Core specs announcements (`open_core_modal`) must never trigger the Final Review modal; Final Review announcements (`open_final_modal`) must be ignored if the session is still in Stage 1 (`core`).
- **The review card must enforce the In-Flight Sync Gate**: If Elena announces opening the final review card while a voice turn extraction is currently in-flight OR before `availableDate` has landed in state, the modal presentation must be latched (`pendingFinalModalOpenRef`) until the in-flight extraction completes. Never render the review card prematurely with newly spoken attributes showing as "Not specified". The gate auto-releases after a 2,500ms safety threshold so the UI never hangs.
- **Coalesced Retry Buffer & Silent Abort Handling**: Live turn extraction requests enforce a 15-second client abort timeout. If an extraction times out or fails, failed turns are buffered and coalesced with subsequent turns so no spoken facts or numbers are lost. `AbortError` must be handled cleanly without logging to `console.error`, preventing Next.js Turbopack dev error overlays.
- **Dynamic AI Pills & Zero-False-Positive Matching in Suggestion Bar**: Custom user choices (e.g. "3-Car Parking", "In 15 Days") must be prepended dynamically with active styling and concise AI badge labels, trimming 1-2 prebuilt options to maintain layout balance. First-word substring matching (`split(" ")[0]`) is strictly banned to prevent false-positive highlights (such as "No Pets" or "No Parking").
- **Two-Step Self-Verifying Post-Call Audit**: End-of-call full-transcript synthesis passes both the complete dialogue and the current live verified state. If discrepancies or contradictions are detected between the live inspector state and the transcript, a 2nd targeted verification pass executes to resolve ground truth and rectify the fields.
- **Telemetry HUD**: Provides full session observability across Agora transcripts, intent triggers, sync gate states, and API latencies with a toggle for dev and production modes.
- **Multi-Device Photo Uplink & Draft Persistence**: Confirming additional specs creates a `status: 'draft'` property record and generates an `uploadToken` with a vector QR code. The mobile upload page (`/properties/upload/[id]`) authenticates via this token without requiring mobile login. The desktop Image Upload Modal short-polls (`/api/properties/draft/[id]/images`) every 2.5 seconds to display incoming photos live. Final deployment activates the draft into `status: 'active'`, preserving all linked media.
- **Server-Side WebP & 1,200px Bounding Box Image Optimization**: All property photo uploads (desktop and mobile QR uplink) process through `sharp` in `src/app/api/properties/upload/route.ts`. Images are strictly converted to WebP format at 85% quality, with dimensions proportionally constrained within a maximum 1,200 × 1,200 px bounding box (`fit: 'inside'`, `withoutEnlargement: true`). Upscaling smaller images is prohibited. Files must be auto-oriented via EXIF and stripped of private GPS/device metadata. Only the optimized `.webp` file is retained on disk; uncompressed raw originals are discarded.
- **Every quoted spoken line in Elena's prompt is a regex target — re-run the patterns before rewording one.** `src/hooks/voice-intents.ts` matches the assistant's speech against a fixed, ordered list and fires the first hit, so the wording of a line in `src/lib/agora-agent-client.ts` decides which card opens. The order is load-bearing: a Stage 4 line containing "core details" … "take a look" matches the core-card pattern, which is checked before the full-review one, and the full review card then never opens on Elena's announcement. Changing a spoken line without running it through those patterns silently reroutes a modal. The core-card patterns match `\d+ core` rather than a literal count, so the number in Elena's announcement can change without breaking the routing — never bake a specific count back into them.
- **An approval is only an approval when the card is on screen.** "Looks good", "that's right" and "continue" are also how an owner ends an ordinary answer, and the approval patterns match the spoken turn before Elena has announced anything. Close and approve intents therefore advance to photo intake only from a visible review card (`confirmFullReview`); a stray approval is logged and dropped. Acting on one used to open the photo uploader mid-intake, which Elena's announcement then closed a second later — a visible flicker with no state to explain it. The card is never stranded: Elena's announcement, the turn extractor and the inspector's Review button all still open it.
- **The owner sees exactly two review cards, never three.** `ReviewSpecsModal` is the only review card: `core` shows the main details, and `additional` / `final` show the whole listing — main details, extra details **and** the nearby places layer, in `src/components/dashboard/onboarding/review/`. There is no separate hyper-local modal, and the stage machine has no hyper-local stage; confirming the full card goes straight to photo intake. Reintroducing a third card puts the owner through two near-identical screens showing the same address and price twice, which is what this merge removed. Elena's prompt promises one card — a new modal between review and photos would be a card she never announces.
- **The full review card never waits on the location search.** The map lookup dispatches at core-spec confirmation and the card opens on the owner's spoken cue, so its nearby-places section owns its own loading, failed and empty states and fills in when the result lands. The sync gate on that card (`pendingFinalModalOpenRef`) is about spoken specs only — gating the card on enrichment would hold Elena's announcement behind a network call she cannot see.
- **Hyper-Local AI Location Intelligence**: When the owner confirms the core specs, background hyper-local enrichment dispatches once, out-of-band, via Gemini with Maps grounding (`src/lib/hyper-local/`). It researches metro transit, highways, landmarks, schools, hospitals, buyer objection playbooks and search tags. It never authors the buyer agent's script; that comes only from end-of-call synthesis. Live spoken corrections from the owner continuously patch the hyper-local HUD and the review card without interrupting Agora WebRTC audio. On publish, `kb_data` is persisted directly into `properties.knowledge_base` (JSONB) on the consolidated `properties` table.
- **Distances come only from Google Routes API. Never let Gemini state a distance.** The Maps grounding tool returns place names, addresses and placeIds, but never a distance or a coordinate, so any figure the model writes is invented. Measured on a fixed address and place: the same query across four runs returned 1.2 / 0.8 / 0.9 / 1.0 km for one hospital, and estimates ran systematically low — a metro station Gemini called "0.5 km" is a 1.4 km walk and a 4.3 km drive around a divided carriageway. Both prompts in `src/lib/hyper-local/` therefore forbid distance language outright; distances are measured afterwards by `measurePlaceDistances` via Routes API Compute Route Matrix (Essentials tier, billed per origin×destination element). Reintroducing a "roughly how far" clause to either prompt silently reverts this. OpenStreetMap/Nominatim was also evaluated and rejected: 6 of 11 real place names returned nothing and "Fr. Agnel School" resolved to a school 21.3 km away, because free geocoders match Indian POI names poorly.
- **Distances are enrichment, never core data — they must fail soft.** A missing `GOOGLE_MAPS_API_KEY`, an unreachable Routes API, or an origin that never geocodes sets `distancesMeasured: false` and omits distances; it must never throw and never take the Agora voice call down. This is a deliberate exception to the fail-fast contract, which governs core property facts.
- **`HyperLocalKbData` name lists are the authority; `nearbyDistances` only annotates them.** The string lists (`nearestMetro`, `topSchools`, `topHospitals`) are persisted JSONB read by the voice agent, the search route and the public listing, so they must keep their shape — distances were added as a separate additive field rather than by converting them to objects. A name with no matching measurement renders without a distance.
- **Only placeIds returned by Maps grounding may be measured.** The structuring pass attaches a placeId to each named place and `selectDistanceTargets` drops any it did not see in the grounding sources. A hallucinated placeId either errors or, worse, resolves to a real but unrelated place and attaches a confident distance to the wrong building. Measuring only the categorised places (never raw grounding chunks) is also what keeps address fragments and the property's own building out of the owner's card and off the bill.
- **The embed map uses a second, public browser key. Never expose the Routes key.** `GOOGLE_MAPS_API_KEY` is server-side, metered, and IP-restricted; it must never gain a `NEXT_PUBLIC_` name or reach the browser. The owner-facing map is Maps Embed API, which is free with unlimited usage, and reads `NEXT_PUBLIC_GOOGLE_MAPS_EMBED_KEY` — inlined into the bundle at build time and therefore public, so that key must be restricted to Maps Embed API only and locked to the site by HTTP referrer. The two keys cannot be merged: a key cannot hold both an IP restriction (needed for server-to-server Routes calls, which send no referrer) and a referrer restriction. Because the VPS builds during deploy, the embed key must exist in the VPS `.env` before `npm run build` or the map affordance silently never appears. The inline map is gated on the key being present, but a map is never *only* available through it: Google Maps URLs (`maps-links.ts`) are plain links needing no key, no quota and no billing, so every place keeps a working "Open in Google Maps" path on a deployment with no embed key at all. Never make the keyless path conditional on the embed key.
- **Location-Based Search & Discovery**: `src/app/api/properties/search/route.ts` performs case-insensitive filtering across `city`, `state`, `listingType`, `price`, and full-text queries against `title`, `address`, `eaScript`, and JSONB `kb_data` search tags. Search and city filtering are integrated into both the Owner Dashboard (`src/components/dashboard/PropertyListingsSection.tsx`) and the Public Discovery Page (`/listings` / `src/components/public/ListingsDiscoveryClient.tsx`).
